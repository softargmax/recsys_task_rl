## 1. Постановка

Есть история пользователей Яндекс Музыки (Yambda-50M): какие треки слушали, какую долю каждого дослушали, органическое это прослушивание или рекомендация. Решение состоит из четырёх шагов:

1. GPT-2 учится предсказывать следующий трек (**SFT**, это политика $\pi$).
2. **Reward model** (RM) по истории и треку-кандидату предсказывает, какую долю трека пользователь дослушает.
3. Политика дообучается через RL (**GRPO**), чтобы рекомендовать треки с высокой предсказанной наградой.
4. Проверяется, стали ли рекомендации лучше на самом деле, а не только по мнению RM.

Главная сложность - шаг 4. RL легко «взламывает» RM (reward hacking), находя треки, которые RM ошибочно оценивает высоко. Поэтому большая часть работы - независимые способы проверить результат.

## 2. Данные и разбиение

**Временное разбиение** по глобальной дате, как в первом задании:

| Часть | Дни от конца данных | Для чего |
|---|---|---|
| test | 0-6 | финальные числа |
| val | 7-13 | выбор моделей и сравнения |
| train | 14 и старше | SFT, RM; контексты для RL берутся из дней 14-27 |

**Защита от утечек.** Всё, что обучается (SFT, RM, GRPO), видит только события train: обучающие окна обрезаются по концу train каждого пользователя, будущее сессии для hit-награды тоже. Каталог и популярность треков считаются только по train, границы бинов заданы константами. Метка «продолжение сессии» у последнего события train считается неизвестной, если следующее событие уже в val/test.

**Каталог:** 50 000 самых частых треков по train, они покрывают 80% прослушиваний. Остальные треки сворачиваются в токен UNK, но событие остаётся в истории с артистом, длительностью и откликом.

**Событие** $e_t$: трек $i_t$, артист $a_t$, доля дослушивания $\text{ratio}_t \in [0, 100]$, органика $o_t$, длительность трека, пауза перед событием.

**Запрос** для оценки - момент, когда старый рекомендатель показал трек ($o_t = 0$) в днях val или test; показанный трек должен быть в каталоге. Контекст - всё до этого момента. На пользователя берётся до 10 запросов, всего около 54 тыс. на test и 55 тыс. на val.

**Listen+** - трек дослушан хотя бы до половины ($\text{ratio} \ge 50$), та же метка, что в первом задании.

## 3. Политика: GPT-2 и SFT

### Вход

Событие кодируется суммой эмбеддингов всех его полей:

$$x_t = E_{\text{item}}[i_t] + E_{\text{artist}}[a_t] + E_{\text{ratio}}[b^{\text{ratio}}_t] + E_{\text{org}}[o_t] + E_{\text{dur}}[b^{\text{dur}}_t] + E_{\text{gap}}[b^{\text{gap}}_t]$$

где $b^{\cdot}$ - номер корзины: ratio разбит на 7 корзин, длительность на 10, пауза на 8. Так модель видит не только *что* слушал пользователь, но и *как*: пропустил или дослушал.

### Выход

GPT-2 (4 слоя, ширина 256, контекст 256 событий) даёт скрытое состояние $h_t$. Вероятность следующего трека - softmax по всему каталогу с общей таблицей эмбеддингов:

$$\pi_\theta(i \mid e_{\le t}) = \operatorname{softmax}_i\left(h_t^\top E_{\text{item}}[i] + b_i\right)$$

### Обучение

Cross-entropy на следующий трек, как в языковой модели:

$$\mathcal{L}_{\text{SFT}}(\theta) = -\frac{1}{T}\sum_{t} \log \pi_\theta(i_{t+1} \mid e_{\le t})$$

**Выбрасывание отклика.** У каждого события окна независимо с вероятностью 0.15 корзина доли дослушивания заменяется на «неизвестно»; трек, артист, длительность и цель обучения не меняются, монетка бросается заново в каждом батче. Зачем: при генерации слейта у сгенерированных треков отклика ещё нет, и они попадают в контекст с «неизвестно». Без выбрасывания модель ни разу не видела бы такого входа при обучении. Если скрыть отклик у реальных треков, NDCG падает всего на 3% (раздел 8.6).

**Результат на val:** NDCG@10 = 0.0237 (MostPop 0.003, «недавно слушал» 0.026). Модель 8 × 512 дала то же качество, поэтому политика - 4 × 256.

## 4. Reward model

### Что предсказывает

Для истории $x$ и трека-кандидата $c$ RM выдаёт ожидаемую долю дослушивания:

$$\hat r(x, c) = \sigma\big(f_\phi(x, c)\big) \approx \mathbb{E}\left[\tfrac{\text{ratio}}{100} \,\middle|\, x, c\right]$$

Вторая голова предсказывает $P(\text{continue})$: продолжит ли пользователь слушать в этой сессии (следующее событие в пределах 30 минут).

### Архитектура

RM - отдельная модель, она лишь инициализируется весами SFT:

```
state  = GPT-2(история)[последняя позиция]                  состояние пользователя
e      = E_item[c] + E_artist[c] + E_dur[c] + E_org[c]        кандидат
m      = Linear(match_features(история, c))                 16 счётчиков совпадений
logits = MLP([state, e, state * e, m]) -> (ratio, continue)
```

**match_features** - 16 чисел без обучения: сколько раз в истории встречались этот трек и этот артист, со взвешиванием по давности $\sum_j e^{-\Delta t_j/\tau}$ для $\tau$ = 1 час, 1 день, 30 дней. Считаются отдельно по всем прослушиваниям и только по дослушанным, плюс «было ли вообще» и «сколько часов назад в последний раз». Это аналог парных признаков «пользователь-трек» из первого задания.

### Обучение

Мягкая бинарная кросс-энтропия с целью $y = \text{ratio}/100$ плюс BCE на продолжение:

$$\mathcal{L}_{\text{RM}} = -\big[y \log \hat r + (1-y)\log(1-\hat r)\big] + \text{BCE}(\hat p_{\text{cont}}, \text{cont})$$

### Ансамбль и базовая модель

- Пользователи делятся пополам. **Член 0** учится на половине A и служит **proxy**: его награду оптимизирует RL.
- **Члены 1-4** учатся на бутстрэп-выборках из A. Их среднее - внутренний судья, разброс - неуверенность для пессимистичной награды.
- **Базовая модель** $\hat b(x, \text{dur})$ видит историю, длительность и органику, но не видит сам трек. Нужна для нормированной награды и для диагностики.

### Две версии RM

| Отложенные показы (val) | AUC Listen+ | GAUC по пользователям | AUC внутри сессии |
|---|---|---|---|
| базовая модель (без трека) | 0.908 | 0.714 | 0.579 |
| RM v1: энкодер 8 × 512 (из большой SFT), совпадения по 256 событиям | 0.909 | 0.723 | 0.598 |
| RM v2: энкодер 4 × 256 (из базовой SFT), совпадения по 4096 событиям | 0.910 | 0.730 | **0.612** |
| CatBoost из первого задания (test) | 0.916 | 0.755 | - |

Зачем v2: 57% следующих треков пользователь уже слушал раньше, но только 11.5% из них попадают в последние 256 событий. Окно 4096 находит 94% таких повторов. Энкодер по-прежнему видит 256 событий, дальняя история идёт только в счётчики. RM v2 меньше, но различает треки внутри сессии лучше: решает длинная история, а не размер энкодера.

**Почему высокий AUC обманчив.** Модель, не видящая трек, даёт 0.908: почти весь AUC объясняется состоянием пользователя («сейчас пролистывает»), одинаковым для всех кандидатов. Для RL важно, как RM ранжирует разные треки в одном контексте, а там она лишь немного лучше базовой (0.598-0.612 против 0.579).

## 5. RL: GRPO

### Слейт и награда

Для контекста $x$ политика генерирует группу из $G = 8$ слейтов (16 для hit-награды). Слейт - $K = 5$ треков, сгенерированных по одному с добавлением в контекст, без повторов. Каждый трек оценивается RM при **реальной** истории $x$, награды складываются с затуханием $\gamma = 0.9$:

$$R(x, a_{1:K}) = \sum_{j=1}^{K} \gamma^{\,j-1}\, r(x, a_j)$$

### Преимущество и функция потерь

Преимущество нормируется внутри группы слейтов одного контекста, отдельная value-сеть не нужна:

$$A_g = \frac{R_g - \operatorname{mean}(R_1, \dots, R_G)}{\operatorname{std}(R_1, \dots, R_G) + \varepsilon}$$

$$\mathcal{L}_{\text{GRPO}}(\theta) = -\frac{1}{BG}\sum_{b=1}^{B}\sum_{g=1}^{G} A_{bg}\sum_{j=1}^{K}\log \pi_\theta\!\left(a_{bgj} \mid x_b, a_{bg,<j}\right) \;+\; \beta\,\frac{1}{BG}\sum_{b,g}\sum_{j=1}^{K} \operatorname{KL}\!\left(\pi_\theta(\cdot \mid s_{bgj}) \,\middle\|\, \pi_{\text{ref}}(\cdot \mid s_{bgj})\right)$$

- Первое слагаемое - policy gradient с групповой базой: повышает вероятность слейтов с $A > 0$.
- Второе - KL-штраф к SFT-модели $\pi_{\text{ref}}$. Он считается **точно**, по всему каталогу из 50k треков, а не оценкой по сэмплу:

$$\operatorname{KL}(\pi_\theta \,\|\, \pi_{\text{ref}}) = \sum_{i} \pi_\theta(i)\,\big[\log \pi_\theta(i) - \log \pi_{\text{ref}}(i)\big]$$

- На каждом батче один шаг градиента, поэтому отношение вероятностей PPO равно 1 и клиппинг не нужен.
- $B = 64$ контекста, lr $2\cdot10^{-5}$, 600 шагов.
- GRPO, генерация слейтов, точный KL и reward model реализованы с нуля в `rl/`, из `transformers` берётся только архитектура GPT-2.

### Что такое β

$\beta$ - сила поводка, который держит политику рядом с SFT. При $\beta = 1$ политика почти не меняется, при 0.1-0.03 сильно уходит от SFT ради награды, при $\beta = 0$ делает всё, что нравится RM. В таблицах **KL** - KL распределения первого рекомендованного трека к SFT, усреднённый по запросам: «насколько далеко ушли».

### Варианты награды $r(x, c)$

| Название | Формула | Идея |
|---|---|---|
| `ratio` | $\hat r_0(x, c)$ | доля дослушивания по proxy |
| `seconds` | $\hat r_0(x, c)\cdot \text{dur}(c) / 240$ | дослушанные секунды |
| `norm` | $\hat r_0(x, c) - \hat b(x, \text{dur}(c))$ | дослушивание сверх ожидаемого для такой длины трека |
| `pess` | $\overline{\hat r}(x, c) - k\cdot \operatorname{sd}\,\hat r(x, c)$ | среднее ансамбля минус неуверенность |
| `continue` | $\hat p_{\text{cont}}(x, c)$ | продолжит ли сессию (прокси удержания) |
| `hit` | $\max_{t \in \text{future}} \mathbb{1}[c = i_t]\cdot \text{ratio}_t/100$ | попал ли трек в реальное будущее сессии, без RM |

### Защиты от взлома

- **CE-якорь** (как ptx в InstructGPT): $\mathcal{L} = \mathcal{L}_{\text{GRPO}} + c\,\mathcal{L}_{\text{SFT}}$ на реальных окнах, $c \in \{0.3, 1\}$.
- **Hit-награда** как добавка к RM: $r = r^{\text{RM}} + w\, r^{\text{hit}}$. Её нельзя взломать: она проверяется по логам, как верификатор ответа в GRPO для математики. В разделе 8.8 она используется отдельно, без RM.
- **Пессимизм ансамбля** (`pess`) и **нормировка по длительности** (`norm`).

### Контроли без RL

- **Best-of-N:** из SFT сэмплируется $N$ слейтов, берётся лучший по proxy. KL такой политики ограничен: $\operatorname{KL} \le \log N - \frac{N-1}{N}$. Это эталон «сколько награды можно получить при данном KL без обучения».
- **Reward-weighted SFT (RW-SFT):** SFT, где лосс позиции умножается на $\exp(\text{ratio}/\lambda)$. Ответ на вопрос «а нужен ли RL вообще».
- **SFT ещё 1-2 эпохи:** отделяет эффект RL от эффекта дополнительного обучения.

## 6. Как проверяется, что стало лучше

### Почему proxy недостаточно

Proxy - та награда, которую оптимизирует RL. Она растёт всегда, в том числе когда политика нашла ошибку RM (закон Гудхарта). Gao et al. (2022) описали это для RLHF количественно: «истинная» награда сначала растёт вместе с proxy, потом падает (**переоптимизация**). Поэтому нужны судьи, которых RL не видел.

### Метрики по логам

Модель ранжирует весь каталог, считается top-10. NDCG@10 считается для каждого запроса и усредняется по запросам. Цели:

| Метрика | Цель |
|---|---|
| `next` | трек, показанный в момент запроса, даже если его пропустили |
| `future` | все различные треки следующих 10 событий той же сессии, органика и рекомендации |
| `lp_next`, `lp_future` | то же, но только дослушанные (≥ 50%) |
| органические дослушанные | дослушанные треки сессии, которые пользователь включил сам |

$$\text{NDCG@10} = \frac{\sum_{k=1}^{10} \mathbb{1}[\text{rec}_k \in \text{цели}] / \log_2(k+1)}{\sum_{k=1}^{\min(|\text{цели}|, 10)} 1/\log_2(k+1)}$$

Главная метрика релевантности - `lp_future`: следующий трек - это часто скип, который старый рекомендатель поставил зря, и модель, угадывающая скипы, выглядит по `next` хорошо. Например, «недавно слушал» выше SFT по `next`, но значимо хуже по дослушанным.

### Другие судьи и поведение

- **Внутренний судья** - члены 1-4 ансамбля. Оказался не независимым: ошибается так же, как proxy, и растёт вместе с ним.
- **CatBoost-судья** из первого задания (раздел 7): другая модель, другие признаки.
- **Поведение:** длительность рекомендованных треков, популярность, доля повторов из истории, доля новых артистов, доля выдачи из топ-100, покрытие каталога, Gini, персонализация (насколько различаются выдачи разных пользователей).

### Статистика

- Сравнение с SFT **парное**: разница считается на одних и тех же запросах, интервал строится для разницы. Парный интервал гораздо уже, чем у двух моделей по отдельности.
- Бутстрэп **по пользователям**, потому что запросы одного пользователя зависимы.
- Таблицы на 10k запросах (8.1-8.5): 200 повторов, `*` - 95% интервал разницы не содержит 0.
- Итоговые таблицы на всех запросах (8.7-8.9): 2000 повторов, двусторонний p-value, **поправка Холма** на все сравнения внутри выгрузки (модели × метрики), `*` - значимо после поправки. Скрипт: `report/significance.py`.

## 7. CatBoost-судья

### Модель

CatBoost из первого задания (уровни L0 + L1, 171 признак) предсказывает Listen+ для показанного трека. Признаки: статистики пользователя, трека, артиста, альбома, пар «пользователь-трек» и «пользователь-артист» по окнам от часа до всей истории, контекст сессии, лайки и дизлайки, коллаборативная фильтрация. На test: AUC 0.916, GAUC 0.755.

### Как он оценивает выдачу политики

Признаки первого задания считаются только для событий из логов, а политика рекомендует треки, которых в логах в этот момент нет. Поэтому для каждого кандидата создаётся **синтетический пользователь**:

1. Для запроса (пользователь $u$, момент $t$) и трека $c$ из top-10 политики создаётся копия пользователя $u$ с его реальной историей до $t$.
2. В конец добавляется строка «пользователю показали трек $c$ в момент $t$».
3. Код признаков первого задания без изменений считает признаки этой строки, CatBoost даёт $P(\text{Listen+})$.
4. Оценка запроса - среднее по 10 трекам, затем парная разница с SFT и бутстрэп по пользователям.

Код признаков взят в том виде, в каком обучалась модель (`judge/task1/`).

### Проверка судьи

На реальных показанных треках судья должен выдать ровно то, что первое задание сохранило в своих предсказаниях. Сверка идёт на test: точное совпадение для 97.8-98.3% треков в разных запусках (300-500 запросов), средняя разница 0.0003; расхождения дают дубликаты событий с одинаковым временем.

### Ограничения

- CatBoost обучен на train+val, поэтому на val его числа немного завышены. Политики между собой на val сравнивать можно, финальные числа - на test.
- Длительность трека есть среди его признаков. Часть «любви к коротким трекам» он может разделять с RM, так что это второе мнение, а не истинная награда.
- Медленный: около 25 минут на 500 запросов × 20 политик на CPU, поэтому оценивается 500 запросов.

### 8.2. Что видно

1. **Взлом награды есть и понятен.** При малом $\beta$ политика рекомендует короткие популярные треки: длительность падает со 190 до 104 с, 99.7% выдачи - топ-100 треков, всем пользователям почти одно и то же. Proxy при этом максимален. Короткие треки действительно чаще дослушивают, и RM это выучила.
2. **Переоптимизация подтверждена независимым судьёй.** CatBoost растёт вместе с KL до KL ≈ 1 ($\beta = 0.1$), затем падает до уровня SFT при $\beta = 0$. Proxy всё это время растёт.
3. **Компромисс релевантности и награды - одна кривая.** NDCG и CatBoost почти однозначно определяются KL. CE-якорь, hit-добавка и пессимизм не сдвигают кривую, а только уменьшают KL, то есть работают как более сильный $\beta$.
4. **Лучшая точка с RM - ratio, $\beta = 0.3$:** CatBoost +0.012, NDCG по дослушанным как у SFT, длительность −23 с. Но на всех запросах NDCG по всем трекам теряет 2-6% (раздел 8.7).
5. **norm закрывает лазейку с длительностью, но проигрывает.** Длительность не меняется, но при том же KL NDCG ниже: без длительности RM почти не различает треки внутри контекста, и политика дрейфует по шуму.
6. **seconds взламывается в другую сторону:** длинные треки (390 с), CatBoost −0.088. Выбор награды задаёт направление взлома.
7. **Best-of-N эффективнее GRPO по proxy на единицу KL.** N=16 (KL слейта ≤ 1.8) даёт proxy слейта 2.863, GRPO β=0.1 при KL 5.1 - 2.837; N=64 (KL ≤ 3.2) - 2.894, больше, чем GRPO без KL-штрафа (KL 40).

### 8.3. Куда уходит точность

NDCG@10 по видам следующего трека, разница с SFT (val):

| | новый трек (43%) | повтор из старой истории (46%) | повтор из контекста (11%) |
|---|---|---|---|
| SFT, абсолютное | 0.0167 | 0.0175 | 0.078 |
| ratio β=0.3 | −0.002 | **+0.002*** | −0.007 |
| ratio β=0.1 | −0.006* | −0.002 | **−0.033*** |
| norm β=0.1 | −0.004* | −0.002 | −0.022* |

RL сильнее всего выталкивает повторы недавних треков: это 11% запросов, но около половины потери NDCG.

### 8.4. RM v2 с длинной историей

| Запуск | KL | CatBoost, Δ | NDCG@10 |
|---|---|---|---|
| ratio β=0.3, v1 → v2 | 0.18 → 0.14 | +0.012 → +0.010 | 0.0232 → 0.0231 |
| ratio β=0.1, v1 → v2 | 1.13 → 0.71 | +0.020 → +0.017 | 0.0165 → 0.0191 |
| ratio β=0.03, v1 → v2 | 7.68 → **2.75** | +0.003 → **+0.018** | 0.0031 → **0.0105** |

- **Более точная RM откладывает переоптимизацию.** При $\beta = 0.03$ с v1 политика коллапсировала, а с v2 судья почти на пике. Это совпадает с Gao et al.: чем лучше RM, тем позже начинается взлом.
- **Кривая «KL против NDCG и судьи» не сдвинулась.** При одинаковом KL результаты те же: новая RM замедляет движение вдоль кривой, но не поднимает её.
- **Вывод:** RM, обученная на логах старого рекомендателя, узнаёт в основном состояние пользователя и длительность трека. Сигнал «какой именно трек нравится» в офлайн-логах слабый. Это ограничение данных, а не архитектуры.

### 8.6. Пять шагов вперёд

5000 реальных цепочек из 5 рекомендаций подряд в одной сессии, test.

**Ошибка RM как симулятора пользователя.** RM предсказывает отклик на k-й реальный трек цепочки. Отклики на треки 1..k-1 в истории либо реальные, либо «всё дослушано» (P1), либо собственные предсказания RM (P2):

| Шаг | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|
| MAE, реальные отклики | 0.166 | 0.164 | 0.159 | 0.156 | 0.158 |
| MAE, «всё дослушано» | 0.166 | 0.219 | 0.240 | 0.253 | **0.263** |
| смещение, «всё дослушано» | −0.005 | +0.105 | +0.147 | +0.170 | **+0.188** |
| MAE, свои предсказания | 0.166 | 0.215 | 0.227 | 0.235 | **0.245** |
| смещение, свои предсказания | −0.005 | −0.064 | −0.080 | −0.095 | **−0.102** |
| AUC, реальные / «дослушано» / свои | 0.93 / 0.93 / 0.93 | 0.93 / 0.91 / 0.91 | 0.94 / 0.90 / 0.91 | 0.94 / 0.88 / 0.91 | 0.94 / 0.86 / 0.90 |

- Ошибка растёт с каждым шагом и к пятому в 1.5 раза больше. Оба протокола смещены **в разные стороны**: «всё дослушано» завышает награду на +0.19, собственные предсказания занижают на −0.10.
- Эти смещения в 5-10 раз больше всего выигрыша RL (около +0.02). Поэтому при обучении каждый трек слейта оценивается при реальной истории, а многошаговая награда офлайн ненадёжна.
- RM v2 ведёт себя так же (MAE на 5-м шаге 0.236 против 0.245).

**Ошибка политики.** NDCG@10 SFT для реального k-го трека цепочки:

| Шаг | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|
| в контексте реальные треки с откликом | 0.0161 | 0.0168 | 0.0190 | 0.0177 | 0.0176 |
| реальные треки без отклика | 0.0161 | 0.0167 | 0.0177 | 0.0169 | 0.0174 |
| собственные выдачи политики | 0.0161 | **0.0106** | 0.0099 | 0.0105 | 0.0099 |

- Незнание отклика почти ничего не стоит (−3%) благодаря выбрасыванию отклика при обучении.
- Свои треки в истории стоят **−40%** уже на втором шаге, но дальше ошибка не накапливается: сгенерированная история сбивает модель один раз - она перестаёт видеть, что пользователь реально слушал последним.

**Поведение при генерации пяти треков.** Повторов внутри слейта нет, награда по шагам почти постоянна. Жадная SFT ставит много повторов из истории (52% на шаге 1, 41% на шаге 5), RL их вытесняет: при $\beta = 0$ остаётся 2-7%. Порядок политик по награде одинаков при всех протоколах, меняется только уровень.

### 8.7. Все запросы: есть ли прирост по логам у GRPO с RM

53.7 тыс. запросов на test и 54.7 тыс. на val, поправка Холма на 32 сравнения в каждой выборке (8 моделей × 4 метрики). Разница с SFT, `*` - значимо после поправки.

| Модель | NDCG по дослушанным, сессия: test / val | NDCG по всем трекам сессии: test / val | NDCG следующего трека: test / val |
|---|---|---|---|
| **RW-SFT** | **+2.3%* / +2.0%*** | +0.6% / +0.4% | −0.5% / −0.8% |
| ratio β=1 | +1.1% / +0.8% | −0.3% / −0.2% | −2.0% / −0.2% |
| ratio β=0.3 | 0.0% / −0.8% | −2.8% / **−3.0%*** | **−6.0%*** / −2.9% |
| ratio β=0.3, RM v2 | +0.5% / −0.6% | −2.1% / **−2.5%*** | **−4.6%*** / −3.2% |
| norm β=0.1, RM v2 | **−11%*** / **−11%*** | **−12%*** / **−13%*** | **−15%*** / **−18%*** |
| ratio β=0.1, RM v2 | **−11%*** / **−15%*** | **−15%*** / **−17%*** | **−21%*** / **−18%*** |
| ratio β=0.1 | **−25%*** / **−25%*** | **−28%*** / **−27%*** | **−34%*** / **−29%*** |

- **GRPO с RM не даёт прироста, который подтверждают логи.** В лучшем случае ($\beta = 1$) он нейтрален. При $\beta = 0.3$ NDCG по дослушанным не меняется, а по всем трекам теряет 2-6%: политика меньше копирует старый рекомендатель, но и новых попаданий не добавляет.
- **CatBoost видит прирост у всех RL-политик (+0.004…+0.018), логи - нет.** Возможные причины: логи не замечают хорошие треки, которых старый рекомендатель не показывал; CatBoost разделяет часть ошибок RM (популярность, длительность). Офлайн это не разрешить.
- Числа посчитаны в fp32 на всех запросах; SFT здесь чуть отличается от 8.5 (0.0325 против 0.0330 по дослушанным на test) из-за другой выборки запросов. Внутри таблицы все модели посчитаны одинаково.

### 8.8. Награда из логов: GRPO на hit-награде

GRPO, где награда - **только** hit (попал ли трек в реальное будущее сессии, с весом по доле дослушивания), без RM, $G = 16$. Плюс RW-SFT с разными $\lambda$ и повтор ratio β=0.3 с другим seed. Все запросы, поправка Холма на 32 сравнения.

| Модель | KL | NDCG дослушанных, сессия: test / val | NDCG всех, сессия: test / val | NDCG следующего: test / val | органические дослушанные: test / val | Длит., с |
|---|---|---|---|---|---|---|
| **GRPO hit, β=0.03** | 0.10 | **+3.2%* / +3.4%*** | **+3.4%* / +3.7%*** | **+4.9%* / +6.2%*** | **+5.0%* / +4.7%*** | 187 |
| GRPO hit, β=0.1 | 0.02 | +2.3%* / +1.3% | +2.1%* / +1.8%* | +3.1%* / +2.9%* | +3.0%* / +3.4%* | 189 |
| RW-SFT, λ=0.25 | 0.03 | +3.0%* / +2.3%* | +0.6% / +0.1% | −1.0% / −2.4% | +6.3%* / +8.5%* | 186 |
| RW-SFT, λ=0.5, 2 эпохи | 0.03 | +2.7%* / +3.0%* | +1.4% / +1.3% | +1.3% / +0.2% | +4.2%* / +6.4%* | 188 |
| RW-SFT, λ=0.5 | 0.02 | +2.3%* / +1.9%* | +0.6% / +0.4% | −0.5% / −1.0% | +4.1%* / +5.8%* | 187 |
| ratio β=0.3, seed 0 | 0.18 | −0.1% / −0.8% | −2.8% / −3.0%* | −5.9%* / −2.9% | −7.0%* / −2.2% | 166 |
| ratio β=0.3, seed 1 | 0.19 | −0.2% / −1.2% | −2.8% / −3.3%* | −6.4%* / −3.7% | −7.1%* / −2.1% | 166 |

- **RL работает, если награда честная.** GRPO на hit-награде значимо улучшает все метрики по логам на обеих выборках (+3…+6%) без сдвига длительности. Тот же алгоритм с выученной RM по логам проигрывает: провал был в награде, а не в RL.
- **RW-SFT стабильно помогает** по дослушанным и органическим трекам (+2…+8%), но NDCG по всем трекам почти не меняет: он перевзвешивает уже известное, а GRPO учится на собственных выдачах.
- **Результат ratio β=0.3 воспроизводится** с другим seed почти до третьего знака.
- **CatBoost-судья с логами не согласен:** GRPO hit β=0.03 у него −0.002 к SFT, RW-SFT +0.005, ratio β=0.3 +0.012. CatBoost предсказывает «дослушает ли показанный трек» и, как RM, ценит короткие и популярные треки; логи меряют «выбрал ли пользователь этот трек». Это разные цели.

|---|---|---|---|
| SFT ещё 1 эпоха | +0.6% / +0.8% | +0.4% / +1.0% | +0.7% / +1.2% |

## 9. Словарь

| Термин | Что значит |
|---|---|
| политика $\pi_\theta$ | модель, выдающая рекомендации (GPT-2) |
| $\pi_{\text{ref}}$ | замороженная копия SFT, к которой тянет KL-штраф |
| слейт | выдача из 5 треков |
| proxy | член 0 ансамбля RM, его награду оптимизирует RL |
| reward hacking | рост proxy за счёт ошибок RM, а не за счёт лучших рекомендаций |
| переоптимизация | истинное качество сначала растёт, затем падает при росте proxy |
| KL | насколько распределение политики отличается от SFT |
| $\beta$ | вес KL-штрафа: больше $\beta$ - политика ближе к SFT |
| advantage $A$ | насколько слейт лучше среднего в своей группе |
| Listen+ | трек дослушан хотя бы до половины |
| GAUC | AUC, посчитанный внутри групп (пользователь, сессия) и усреднённый |
| парный бутстрэп | интервал для разницы двух моделей на одних и тех же запросах |
